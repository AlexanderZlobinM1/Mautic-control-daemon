# MCD — необязательная защищённая доставка материалов сервиса

Дата предложения: 2026-10-01. Постановка: Александр.
Статус: уточнённое требование хранения и проект модели; алгоритмы, lifecycle ключей и политика недоступности
сервиса не приняты и не реализованы. Не условие запуска общего формата пакетов.

[Формат пакета](MCD_V2_PACKAGE_FORMAT.md) · [Сценарии](MCD_V2_SCENARIO_PACKAGES.md)

## Цель и граница

Окончательное уточнение Александра: объект защиты — исходный скрипт/сценарий
и его внутренняя логика. Результат применения не является объектом защиты.
Нужно предотвратить прямое чтение и распространение сохранённого исходника,
сохранив исполнение MCD через расшифровку только в памяти. Не превращать
это требование в шифрование результата, всей инсталляции или клиентской БД.
Конфиденциальность не расширяет grants сценария и не разрешает произвольный
root-shell вместо согласованного typed executor/extension protocol.

Уточнение Александра: файлы защищённого пакета на диске всегда encrypted.
MCD открывает нужные ресурсы на лету в памяти; ключ предполагается получать
по API и хранить только в памяти. Расшифрованный архив, SQL/скрипт или временный
plaintext файл пакета на диске не создаётся. Речь о содержимом пакета, а не
о невозможности наблюдать результаты его применения в файлах/БД инстанса.

Отдельные материалы коммерческого сервиса, не предназначенные для публичного
распространения, могут доставляться как encrypted payload. Descriptor остаётся
доступным для discovery; защищённое содержимое открывается при получении доступа
у сервиса. Пользовательские/community пакеты остаются открытыми и не требуют
подписки, ключа SalesSnap или обращения к коммерческому порталу.

Это контроль выдачи материалов и защита транспортной/сохранённой копии, а не
обещание DRM или невозможности копирования на сервере клиента. Клиентский
администратор может извлечь ключ/память или сохранить plaintext после открытия.
Применённый file patch оставляет открытые изменения файлов Mautic; DB операция
тоже не становится секретной только потому, что исходный SQL был зашифрован.
Правило нераспространения, если требуется, должно сопровождаться условиями
сервиса; криптография не обеспечивает его на подконтрольном клиенту хосте.

## Разделение ключей

### Партнёрские защищённые каналы

Уточнение Александра: механизм нужен в том числе будущим партнёрам
коммерческого сервиса, которые захотят защищённое распространение своих
материалов. Это общая capability доставки, не SalesSnap-specific DRM.

Пакет указывает publisher/channel identity и режим ресурса (`plain` либо
`encrypted`); общий provider boundary обслуживает их обоих. Коммерческий
портал может выступать посредником партнёрской выдачи, либо использовать
согласованный совместимый provider. Конкретная модель партнёрства/прав сервиса
не выбирается автоматически этим документом.

Endpoint получения ключа и credentials выбираются из доверенного подключения
провайдера, а не из произвольного URL внутри downloaded пакета. API token
SalesSnap не отправляется партнёру автоматически; учётные данные ограничены
своим сервисом. Проверяется binding publisher/channel/package revision/recipient
при выдаче ключевого материала. Один партнёр не получает доступ к секретам
другого, локальному instance DB credential или host grants.

Пользователь один раз подключает используемый сервис; если партнёры обслуживаются
через единый коммерческий портал, дополнительные ключи каждого партнёра не
запрашиваются вручную. Прямое отдельное подключение — самостоятельный credential
для того провайдера, а не повторное использование одного API token везде.

Происхождение и publisher видны в обычной информации о пакете. Шифрование
прозрачно для запуска; plain/community packages сохраняют открытый workflow.
Партнёрские channels не разрешают пакету обойти scoped executor/grants и не
превращают MCC в коммерческий портал. Доставка и атрибуция утечки ведутся
по конкретному provider/channel; разделение ownership и lifecycle ключей
должно быть подтверждено при последующем security review.

Предложение Александра использовать один личный ключ как API credential и
ключ расшифровки требует изменения: это разные назначения и lifecycle.

- API token — аутентификация клиента к коммерческому сервису; отзываемый,
  сменяемый и ограниченный по области действия. Не использовать как DEK.
- Client/instance identity — связывает выдачу ключа с получателем, отдельно
  от долгоживущего API token. Ключевая пара — возможный способ доставки,
  не обязательное уже принятое решение.
- Content DEK — случайный ключ encrypted payload. Сервис оборачивает его для
  выбранной client/instance identity после проверки права получить материал.
  Индивидуальным может быть key envelope, а не весь большой payload архив.

Не разрабатывать свой cipher. Использовать проверенную authenticated encryption
и библиотеку; bind package ID/revision/content digest/recipient к envelope.
Encrypted payload digest и plaintext resource digests — разные поля с явно
описанным покрытием. Hash не шифрует и сам по себе не доказывает издателя.
Подпись/publisher verification рассматривается отдельно от confidentiality.

## Получение и исполнение

### Прозрачность для пользователя

Прямое требование Александра: легальный пользователь один раз вводит ключ
подключения к сервису. Далее обычный и encrypted пакет имеют одинаковый
пользовательский путь: выбор операции → запуск → progress → результат.
Не нужны отдельные decrypt кнопки, ручное получение content keys, повторный
ввод API credential на каждый пакет или показ криптографической обвязки.

Введённый credential сохраняется штатным защищённым механизмом MCD, а не в
пакете/обычном журнале. Технически API credential и content encryption keys
разделены, но пользователь не обязан ими управлять: MCD автоматически получает
нужный краткоживущий ключ и открывает ресурсы в памяти. После перезапуска MCD
повторный ввод не требуется, пока подключение действительно и credential не
отозван/сменён. Безопасный storage/lifecycle ещё требуется реализовать.

При недоступности сервиса/отзыве доступа показывается обычная понятная ошибка
доступа и действие для восстановления подключения, не техническая ошибка cipher.
Offline/grace policy остаётся открытым вопросом; прозрачность не является
обещанием исполнения закрытых материалов без необходимого доступа к сервису.
Сервис ценен в целом, отдельные утечки приняты оператором как соразмерный B2B
риск; защита не должна ухудшать обычный workflow или стать целью продукта.

1. MCD регистрирует открытый descriptor, команды и availability metadata.
   Это не делает encrypted операции автоматически исполнимыми.
2. При выборе конкретной revision получает encrypted ресурсы и соответствующий
   ключ/ключевой envelope от провайдера по аутентифицированному защищённому API.
   API token не используется непосредственно как content key и не входит
   в пакет/run logs. Ответ с key material также не журналируется/кешируется.
3. Сервис проверяет подписку при выдаче envelope/ключевого материала, если это
   часть доступа к его закрытым ресурсам. Агент не вводит global subscription
   gate для всех операций или community пакетов.
4. MCD проверяет envelope/ciphertext, открывает необходимые ресурсы в памяти,
   сверяет plaintext digest и исполняет через тот же scoped executor.
5. Не записывает plaintext ресурсы пакета/ключи на диск, включая temp cache,
   subprocess argv, debug logs и crash artifacts. Передача driver через
   поддерживаемый in-memory/stream protocol. Если driver требует plaintext
   pathname и не поддерживает такой протокол, он не считается совместимым
   с confidential resource: нельзя молча создать временный открытый файл.
6. Key material ограничен нужным run/resource; освобождается после применения.
   До реализации определить lifetime, wipe behavior и требования против
   swap/core dumps. Не обещать гарантированную очистку RAM обычного runtime
   без доказательства; защита от администратора хоста всё равно не достигается.

«Расшифровка на лету» означает in-memory lazy opening выбранных ресурсов, не гарантию
нераспространения. Если клиент один раз получил долговечный DEK, остановка
подписки не делает уже доступное содержимое криптографически недоступным.
Сервис может прекратить выдавать новые ресурсы/ключи; не может гарантированно
удалить сохранённый клиентом plaintext или ключ без контроля его системы.

File patch открывается в памяти, но исправленный application file на диске
остаётся обычным файлом Mautic. Composer/vendor или ZIP target files тоже
должны быть доступны штатному runtime инстанса после установки. Поэтому
«никогда plaintext на диске» относится к закрытому содержимому сценария;
нельзя обещать его для всех конечных файлов обновляемого приложения.

Не отменять работающий run посреди изменения БД из-за истечения подписки.
Не включать native cron одновременно с MCD из-за ошибки получения ключа.
Политика для cached material, новых runs, offline/grace, expiry и recovery
должна быть явной до реализации, а не скрытым поведением licence check.

## Открытые вопросы

### Персональная выдача и отзыв доступа

Уточнение Александра: защита не обязана предотвращать любое извлечение.
Цель также — связать утёкшую копию с получателем и отозвать его доступ к сервису.

Предложение: каждой выдаче присваивать opaque `delivery_id`, recipient/instance
binding, package revision и точный ciphertext/envelope digest. Сервис хранит
связь delivery с аккаунтом; recipient metadata аутентифицируется и связывается
с ciphertext, а не является заменяемым текстовым полем. В открытый descriptor
не помещать персональные данные клиента. Общий plaintext package digest
и индивидуальный delivery digest различаются; переупаковка для получателя
не должна подменять логическую package revision.

Утечка исходного encrypted delivery позволяет установить, кому сервис выдал
эту копию, по записи выдачи. Утечка одинакового для всех plaintext скрипта
сама по себе этого не позволяет: для данного случая нужна индивидуальная
метка внутри исходника (например, inert watermark), не меняющая поведение.
Схему маркировки надо отдельно проверить для typed scripts/code extensions:
простая удаляемая метка не является гарантированной атрибуцией любой утечки.
Идентификация выданной копии не автоматически доказывает намеренную утечку
её получателем; не обещать больше фактической связи выдачи.

Отзывается service API credential/разрешение на будущую выдачу key material.
Сервис перестаёт предоставлять новые скрипты, revisions и ключевые envelopes
этому получателю. Уже сохранённый plaintext/DEK криптографически не отзывается.
Не заявлять обратное и не прерывать изменение инстанса в середине run.
Эта мера относится только к закрытым материалам сервиса, не к возможности
писать и исполнять собственные/community пакеты в MCD.

| Вопрос | Требуется решение |
| --- | --- |
| Какие материалы закрыты | Список категорий сервиса; не объявлять все пакеты платными |
| Account или instance identity | Граница распространения, перенос хоста, recovery и смена ключей |
| Online выдача или cached envelopes | Что доступно после отключения сети/истечения подписки |
| Потеря ключа | Повторная выдача/перешифрование без потери клиентских данных |
| Plaintext workflow | Файловые/SQL/extension drivers, transient storage и журналирование |
| Поддержка поставщиков | Расширение общего provider API, не привязка core MCD к SalesSnap/MCC |
