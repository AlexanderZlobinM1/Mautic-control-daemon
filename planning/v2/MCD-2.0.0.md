## Назначение

Решение Александра, 2026-09-27: версия 2 — рубеж готовности существующего MCD. Доработки постепенно выпускаются в v1; после закрытия согласованной обязательной части чеклиста меняется номер на 2. Для систем это очередная обычная версия. Смена цифры сама по себе не требует нового продукта, исполнителя, протокола или специальной миграции.

## Обязательное направление: частные правила вне кода

Прямое требование Александра, 2026-10-02: подготовка к версии 2 включает
постепенное вынесение существующего хардкода из MCD/MCC. Новые частные правила
зашивать в исходники запрещено. IP, хосты, порты, списки исключений, версии
зависимостей, матрицы совместимости, сценарные шаги и условия отображения
частных действий хранятся во внешней редактируемой политике, матрице или пакете.
Менеджер MCC — один из поставщиков этих данных, а не обязательная часть агента.

В коде остаются универсальные механизмы исполнения, проверки формата,
разграничения полномочий, состояния и результата. Формат протокола и инварианты
безопасности не превращаются в произвольный исполняемый код из конфигурации.
Изменение частного правила не требует релиза MCD/MCC; новый универсальный
примитив может потребовать изменения исполнителя.

- [ ] Существующий хардкод инвентаризирован с путями, владельцами и заменяющими внешними данными.
- [ ] Каждый перенесённый путь использует внешние данные; прежняя частная ветка удалена после доказанной замены.
- [ ] Изменение правила во внешних данных проверено без пересборки или обновления MCD/MCC.
- [ ] Review новых изменений отклоняет частные source defaults, скрытые fallback и специальные ветки по IP/host/version/ID.

Срочный firewall — применение этого требования: адреса и правила внешние;
реализуется только доказанно отсутствующее общее применение политики.
Чеклист пока открыт. Это не разрешение немедленно переписать все компоненты
или возобновить приостановленные задачи; перенос выполняется в разрешённых работах.

MCD 2.0.0 — следующая версия существующего MCD, а не отдельный daemon-проект.
Она должна впитать все существующие наработки v1 и сохранить управляемую работу
с MCC. Новая версия готовится к публичному продвижению; открытость исходников
уже существует, но продукт должен стать пригодным для самостоятельного конечного
пользователя без обязательного MCC.

## Основные возможности

1. Полная подготовка голой системы с нуля для установки и работы Mautic.
2. Самостоятельная работа MCD без MCC. Платная поддержка и личный веб-кабинет
   предоставляют патчи и дополнительные сервисы.
3. Веб-управление самостоятельной инсталляцией и установка плагинов через
   личный кабинет. Существующий путь через MCC также сохраняется.
4. Основная аудитория самостоятельного предложения — конечный пользователь
   одной инсталляции, а не оператор массового парка.

## Границы компонентов

MCD остаётся существующим компонентом с новой major-версией. Инфраструктурная
обвязка платной поддержки и личного кабинета — отдельный будущий проект.
Его основание — MCC, включая API и общие механизмы. Общий код должен быть явно
связан и переиспользован; различия пользовательского продукта должны быть
выделены, а не скрыты в копии MCC. Механизм переиспользования пока не выбран.

Уточнение Александра, 2026-10-21: коммерческий Portal не является альтернативным
MCC и не подключает клиента напрямую к MCC. Он является посредником между
клиентом и MCD: клиентский MCD сам устанавливает outbound-соединение с Portal,
получает задания и возвращает receipts. MCC остаётся единым каталогом и
источником plugins/fixes/patches/packages; MCD скачивает разрешённые подпиской
immutable artifacts из MCC по scoped-разрешению Portal. Каталог, publisher и
executor не дублируются. Полная граница: [коммерческий control plane](MCD_V2_COMMERCIAL_CONTROL_PLANE.md).

## Стратегия и общая продуктовая основа

Уточнение Александра, 2026-09-26:

- MCD сохраняется open source и активно продвигается в сообществе Mautic.
  Цель — репутация, участие сообщества и развитие общественного проекта при
  сохранении ведущей роли нашей команды в его направлении и сопровождении.
  Ожидаемый эффект — снижение собственных издержек инфраструктуры и поддержки
  MCD через участие сообщества; это гипотеза, а не гарантированный результат.
- MCD уже служит основой собственных проектов, включая «маутикрфп»
  (название сохранено из постановки; точное написание уточнить позже) и будущий
  SaaS SalesSnap. Развитие MCD нужно всем этим продуктам, поэтому инвестиции
  должны усиливать общую основу без распыления и отдельных дублирующих реализаций.
- Платная подписка расширяет охват рынка. Преимущество нашей команды — уже
  работающий MCC и накопленные решения. API и open source не должны искусственно
  закрывать возможность другим разработчикам создавать аналогичные продукты.

## Клиент подписки и предложение

Подписка предназначена для клиентов, которые хотят держать инсталляцию и данные
под собственным контролем; Александр привёл «Алиделу» как пример такого клиента.
Клиент остаётся владельцем и оператором своей среды. Мы предоставляем удобный
инструмент управления конфигурацией, доступ к нашим плагинам, backup и upgrade,
простую оплату и оперативную техническую поддержку.

Любая поддерживаемая операция должна оставаться доступной через консоль/API.
Кабинет предоставляет проверенный сценарий с понятным ожидаемым результатом,
вместо самостоятельного поиска решений, подбора команд и ручной работы по SSH.
«Один клик» означает удобное выполнение проверенной операции; точные гарантии,
предусловия, диагностика и восстановление после ошибки ещё требуют проектирования.

## Модель ответственности и риска

Предлагаемая модель отличается от SaaS размещения: клиент сам управляет средой
и выполняет действия, сервис предоставляет средства управления и поддержку.
Ожидается меньший объём рисков и обязанностей вокруг клиентских данных и
чувствительных операций. Это стратегическая гипотеза, а не вывод об отсутствии
GDPR или иных обязанностей.

До реализации отдельно определить фактические потоки данных и доступов:
что получает кабинет/API, какие сведения попадают в телеметрию, backup,
платёжный сервис и поддержку, и когда специалист получает доступ к среде.
Не предполагать ни обязательное размещение клиентских данных у нас,
ни отсутствие ответственности без проверки выбранной архитектуры.

## Преемственность v1

Перед реализацией составить инвентаризацию всех функций, контрактов и
эксплуатационных наработок v1 с отображением в v2. Ни одна существующая функция
не считается отменённой автоматически. План должен отдельно описать standalone
поведение и поведение под MCC, обычный выпуск следующей версии и совместимость существующих
инсталляций. Специальная миграция только из-за цифры 2 не требуется.

## Опциональные плагины MCD — утверждённый план 1.8 и 2.0

Решение Александра, 2026-11-01: универсальный механизм плагинов MCD и
перечисленные ниже дополнения входят в план 1.8 и сохраняются в требованиях
2.0. Сейчас механизм не реализовывать: рубеж 1.7 — разделение ядра и внешней
обвязки с сохранением работающего поведения. Это не плагины самого Mautic.

Плагины необязательны для базовой работы Mautic и устанавливаются по
необходимости. Согласованный состав:

| Плагин / группа | Назначение |
| --- | --- |
| Wazuh | Интеграция с используемым нами окружением безопасности |
| Zabbix | Внешний мониторинг |
| Fail2ban и управляемые блокировки | Дополнительная защита хоста |
| Cloudflare | Специфические настройки прокси, real IP и связанные интеграции |
| Локальный почтовый сервер | Postfix/Sendmail/OpenDKIM для выбранного локального транспорта |
| Почтовые провайдеры | Специфические интеграции и зависимости, включая Amazon mailer |
| Внешние хранилища резервных копий | Коннекторы S3, SFTP и других хранилищ |
| Специфические кластерные интеграции | Galera/PXC, репликация и маршрутизация |
| Внешние уведомления | Telegram, Slack, webhook и другие каналы |

Начать отработку универсальности в 1.8 с Wazuh и Zabbix, затем переносить
остальное постепенно. Общий lifecycle: установка, включение, настройка,
проверка состояния, обновление и отключение. Отключение само по себе не
удаляет данные и не останавливает/удаляет установленный системный сервис.

Плагин добавляет возможность; его системная установка и настройка исполняются
внешними сценариями. Обязательные для выбранной установки PHP, БД и веб-стек
остаются сценариями и не становятся опциональными только из-за этого механизма.
В ядре остаются обнаружение/идентификация инстансов, команды Mautic,
кольца/очереди/планировщик, общий исполнитель/кеш/результаты и общие механизмы
блокировок, резервирования и восстановления.

Wazuh в нашем действующем окружении сохраняется без регрессий. Портальный
Own host работает без Wazuh. Опциональность для других хостов не снижает
требований сохранения нашей работающей интеграции.

Добавление этого раздела фиксирует утверждённый план, но не запускает
реализацию 1.8, новые проекты или работников. Детали формата и совместимости
плагинов ещё предстоит определить без дублирования существующего исполнителя.

## Ordinary scheduler debug cycle (operator clarification, 2026-10-03)

- Debug belongs to the ordinary MCD scheduler, including standalone mode; MCC supplies editable policy, not another planner.
- A captures compact input/state before the frozen assigned pool, B follows all initial terminal outcomes, then a full native command without IDs produces C.
- Existing rings, SQL paths, priority and parallelism are unchanged; repeats do not expand the pool, reset its boundary or overwrite initial failures.
- Segment, campaign rebuild/update and trigger have independent cycles; no same root/type overlap, including native-process recovery after restart.
- Period, per-operation windows, subset and retention are external runtime policy; three hours is a policy value, not source hardcode.
- Evidence includes indexed ID/state/hash samples, task generations/outcomes, code/settings identity, timing and explicit caps/unknown/errors; counts and return code alone are not correctness proof.
- Live customer trigger execution needs explicit permission. Obsolete external comparator/full-cycle/producer/logging entrypoints are retired, without deleting existing host evidence.
